# Reservation Schema Documentation

The **Reservation Service** manages this schema to track event bookings. It decouples its relational structure from other microservice databases by tracking user ownership through plain String identifiers (`authUserId`) instead of internal `ObjectId` populates.

## Schema Definitions

| Field | Type | Required | Unique | Details / Validation |
| :--- | :--- | :---: | :---: | :--- |
| `_id` | ObjectId | System | Yes | Primary Key automatically generated by MongoDB. |
| `authUserId` | String | Yes | No | Trimmed reference ID matching the account holder entity managed by the Authentication Service. |
| `eventTitle` | String | Yes | No | Trimmed descriptive title or name of the booked reservation. |
| `reservationDate` | Date | Yes | No | Explicit calendar date and timestamp scheduled for the event. |
| `numberOfGuests` | Number | Yes | No | Expected attendee count. Constraints: Minimum validation threshold of `1`. Defaults to `1`. |
| `status` | String | Yes | No | Booking operational state flag. Enum values: `["pending", "confirmed", "cancelled", "completed"]`. Defaults to `pending`. |
| `createdAt` | Date | System | No | Timestamp when the booking entry was first saved. |
| `updatedAt` | Date | System | No | Timestamp when the booking entry parameters were last modified. |

## Database Indexing

### Compound Unique Index
To protect transactional data integrity at the database level, a unique compound index is enforced to prevent double-booking conflicts:

```javascript
// Prevents duplicate bookings for the exact same event title on the same date/time
reservationSchema.index({ eventTitle: 1, reservationDate: 1 }, { unique: true });
